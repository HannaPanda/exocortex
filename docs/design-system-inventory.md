# Design-system inventory

The audit behind issue #124 (epic #123). It records what the interface owns
today, which implementation of each concept is canonical, where two exist, what
is only implicit, and which questions are still open. It is the input for the
living styleguide (#125), the experiments (#126), the regression gates (#127)
and the governance rules (#128).

It is not a second `DESIGN.md`. The rules and their reasons stay there; the
token lookup stays in `docs/ui-system.md`. This file says where each thing
lives and in what state it is. The audit changed no production UI, with one
exception that was a defect rather than a design question: the missing
`--shadow-lg` token (see F-5), fixed separately in `0ebed50`.

Counted on 2026-09-24 at `70143c0` over `apps/web/src` and `packages/ui/src`,
tests excluded. Every finding names a file so it can be recounted rather than
believed. Where the dated review `docs/design-review-2026-09-20.md` has gone
stale, this file says so.

## 1. Taxonomy

Every entry below carries one or more of these levels. The styleguide's
navigation (section 6) is built from the same list, so a level without entries
there is a level without a page.

| #   | Level                    | Answers                                                    |
| --- | ------------------------ | ---------------------------------------------------------- |
| 1   | Principles               | what the interface is for, in one screen (`PRODUCT.md`)    |
| 2   | Foundations              | colour, type, space, radius, elevation, icons, layout      |
| 3   | Design tokens            | the named values in `tokens.css` and `styles.css`          |
| 4   | Components               | the exports of `@exocortex/ui`                             |
| 5   | Component states         | hover, focus, active, selected, disabled, loading, invalid |
| 6   | Patterns                 | recurring combinations: empty state, confirmation, row     |
| 7   | Layouts                  | shell, content page, editor, settings, admin, table view   |
| 8   | Responsive behaviour     | what each surface does at desktop, ~768 px, ~390 px        |
| 9   | Accessibility            | focus, keyboard, names, live regions, composite widgets    |
| 10  | Content / UI language    | labels, confirmations, errors, dates, counts, terminology  |
| 11  | Interaction and motion   | the curve, the durations, press, enter and exit            |
| 12  | Usage rules / Do & Don't | the named rules in `DESIGN.md`                             |
| 13  | Testing / regression     | what guards each entry today                               |
| 14  | Governance               | how a new entry is admitted (#128)                         |

### Status values

| Status                  | Meaning                                                                      |
| ----------------------- | ---------------------------------------------------------------------------- |
| `canonical`             | one implementation, used as intended, documented                             |
| `partial`               | canonical, but a relevant state, variant or call-site group is missing       |
| `duplicate`             | two or more implementations of the same concept                              |
| `inconsistent`          | one implementation, applied in contradictory ways, or code and rule disagree |
| `missing`               | the concept recurs and has no shared implementation                          |
| `needs-design-decision` | two plausible answers; the choice is visual, not technical                   |

## 3. Gaps

Concepts that recur without a shared implementation, most call sites first.

1. **Field**: label, control, help text, error, with the `aria-describedby` and
   `aria-invalid` wiring `SettingRow` already does. ~16 loose error paragraphs
   and every dialog form would use it.
2. **Confirmation**: one confirm pattern for destructive actions, and a decision
   which actions need it (four currently have none).
3. **Tone on status components**: warning, success, info on `Alert`, `Badge`,
   `Progress`; 14 hand-applied uses of those tokens.
4. **Status vocabulary for runs**: one mapping from a job, run or build state to
   label and badge, shared by render, automations and projects.
5. **Formatting helpers**: one module for absolute dates, times, durations and
   numbers in `de-DE`.
6. **Page header**: title plus lead, repeated ~20 times.
7. **Navigation group**: one shape for secondary navigation, or a written rule
   for when each of the six applies.
8. **Popover surface**: the shared class for editor listboxes that cannot use
   `Popover` because Tiptap positions them.
9. **Loading on Button**, compact `EmptyState`, `Kbd`, z-index scale.
10. **A narrow contract for dense surfaces** (P12).
